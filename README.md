# 주간 감정 회고 (Diary Analyzer)

하루 일기를 쓰면 AI가 감정을 분석하고, 일주일치를 모아 감정 흐름과 주간 리포트를 보여주는 개인 프로젝트입니다. 전역 후 AI/정보통신 역량을 다시 쌓기 위해 시작했고, 현재는 소규모(10명 이내) 시범 서비스로 운영 중입니다.

> ⚠️ AI 분석은 참고용이며 의학적 진단이 아닙니다.

## 주요 기능

- 별명 + PIN 로그인 (초대 코드 기반 가입)
- 날짜별 일기 작성과 저장, 일기별 감정 점수·키워드·한 줄 요약 분석
- 내 기분 점수 직접 입력 + AI 점수와 비교하는 그래프
- 감정 변화 그래프, 키워드 빈도 그래프
- AI 주간 리포트 생성
- AI 서버가 막혀도 일기는 먼저 저장되고, 나중에 다시 분석 가능 (모델 자동 탐색 + 재시도)
- 하루 AI 사용 횟수 제한 (사람별 + 전체 합산, 한국 시간 기준)
- 동의 화면, 내 데이터 내려받기(JSON/CSV), 일기·계정 삭제
- 새로고침(F5)해도 로그인이 유지되는 세션 쿠키 (시간 기반 토큰 회전 + 재사용 탐지)
- 일기 본문은 암호화되어 저장

## 기술 스택

Python, Streamlit, pandas, Google Gemini API, MySQL, cryptography(Fernet), PyMySQL

## 실행 방법

1. 저장소를 내려받습니다.
2. 가상환경을 만들고 켭니다.
3. 라이브러리를 설치합니다.
4. `.env.example`을 복사해 `.env`로 이름을 바꾸고, 아래 값을 채웁니다.
   - `GEMINI_API_KEY`: Google AI Studio에서 발급
   - `INVITE_CODE`: 가입 시 필요한 초대 코드 (직접 정함)
   - `ENCRYPTION_KEY`: 일기 암호화 키 (`python -c "from cryptography.fernet import Fernet; print(Fernet.generate_key().decode())"`로 생성)
   - `MYSQL_HOST`, `MYSQL_PORT`, `MYSQL_DB`, `MYSQL_USER`, `MYSQL_PASSWORD`: MySQL 접속 정보
5. 샘플 데이터를 만들고 실행합니다.

## 배포

Streamlit Community Cloud에 배포할 때는 위 `.env` 항목을 앱 설정의 **Secrets**에 TOML 형식(모든 값에 큰따옴표)으로 동일하게 등록합니다. MySQL은 Railway 등 외부 호스팅을 사용해, Streamlit 컨테이너가 재시작되어도 데이터가 유지되도록 합니다.

## 데이터와 보안

- 일기 본문은 `ENCRYPTION_KEY`로 암호화되어 MySQL에 저장됩니다. **이 키를 잃어버리면 기존 일기를 복구할 수 없습니다.**
- PIN은 원문이 아니라 PBKDF2 해시로 저장됩니다.
- 로그인 유지 토큰은 해시로 저장되며, 발급 후 1시간이 지나면 다음 사용 시 자동으로 새 토큰으로 교체됩니다. 교체된 옛 토큰이 다시 사용되면 재사용 공격으로 간주해 해당 계정의 모든 세션을 강제 종료합니다.
- 일기 내용은 분석을 위해 Google Gemini API로 전송됩니다. 무료 구간에서는 입력이 학습에 쓰일 수 있어, 실명·연락처 등 특정 가능한 정보는 입력하지 않도록 안내하고 있습니다. (이 앱의 삭제 기능은 자체 DB에서만 유효하며, 이미 전송된 데이터의 삭제는 보장하지 않습니다.)
- 일기 데이터(`data/`)와 API 키(`.env`)는 `.gitignore`로 저장소에서 제외됩니다.

## 개인정보와 사용량 제한

- 가입 시 동의 화면을 거치며, 동의 문구가 바뀌면 `CONSENT_VERSION`을 올려 재동의를 받습니다.
- '내 정보' 탭에서 본인 데이터 내려받기(JSON/CSV), 일기 전체 삭제, 계정 삭제(탈퇴)가 가능합니다.
- 하루 AI 사용 횟수는 사람별(일기 분석 2회, 리포트 1회)과 전체 합산(분석 20회, 리포트 10회)로 제한됩니다. 분석 실패 시 제한적으로 횟수를 돌려줍니다.

## 겪은 문제와 배운 점

### 환경 설정 단계

- `GEMINI_API_KEY=...` 같은 `.env` 내용을 터미널에 직접 입력해 "명령어로 인식할 수 없다"는 오류를 겪고, `.env`는 파일에 적는 내용이지 터미널 명령이 아니라는 걸 구분하게 됨
- `.env`, `test.py` 같은 파일이 `venv` 폴더 **안에** 생성되어 "파일을 찾을 수 없다"는 오류가 반복됨 → 가상환경 폴더와 실제 작업 파일의 위치를 분리해야 한다는 걸 배움

### AI 모델 연동 단계

- `gemini-2.5-flash` 모델이 신규 사용자에게 서비스가 종료되어 404 오류 발생 → 오류 메시지가 알려주는 대체 모델로 교체
- 무료 API 한도 초과로 503(서버 과부하) 오류가 반복됨 → 한 모델만 고정하지 않고, 사용 가능한 모델을 자동으로 조회해 순서대로 시도하고 재시도하는 구조(`ai_client`/`analyze.py`)로 전환
- "저장 먼저, 분석 나중" 구조를 도입해, AI 서버가 붐벼도 나중에 서버가 한산할 때 분석할 수 있도록 설계함

### 코드 구조화 단계

- 한 파일(`app.py`)에 파일 저장, AI 호출, 화면 로직이 모두 섞여 있어 유지보수가 어려워짐 → `config`, `storage`, `analyze`, `report`, `ui_*` 등 역할별 모듈로 분리
- 이후 `backend`/`frontend`/`scripts` 폴더로 한 번 더 재구성, 이후 `backend` 내에서 `db`폴더를 하나 더 생성해 db관리를 더욱 보기 쉽게 정리함

### 배포 환경 전환 단계

- Streamlit Community Cloud는 컨테이너 기반이라 재배포·재시작 시 로컬 파일(JSON, SQLite)이 초기화될 수 있다는 점을 알게 되어, 저장소를 SQLite → MySQL(Railway)로 전환
- Railway MySQL 연결 시 `MYSQLHOST`가 내부 전용(Private) 주소임을 모르고 접속을 시도해 실패 → Public Networking 설정에서 별도의 외부용 호스트·포트를 찾아야 한다는 걸 배움
- Streamlit Secrets는 `.env`와 달리 TOML 문법을 쓰며, 모든 값에 큰따옴표가 필요하다는 걸 "Invalid format" 오류로 알게 됨

### 성능과 동시성

- Railway MySQL 연결 후 응답이 눈에 띄게 느려짐 → 매 요청마다 새로 접속하고 끊던 구조를, 연결을 재사용하고 끊겼을 때만 재연결(`ping(reconnect=True)`)하는 구조로 바꿔 동시 접속 안전성을 높임 //그러나 여전히 처음 접속할 때의 느려짐을 해결하지는 못하는 한계 발생

### 보안 점검과 개선

- F5 새로고침 시 로그인이 풀리는 문제를 해결하려고 로그인 토큰을 주소창(`?token=...`)에 저장하는 방식을 처음 도입했으나, 이 방식 자체가 브라우저 기록·Referer·스크린샷 공유를 통해 토큰이 노출될 수 있는 결함이라는 걸 발견함
- 이를 해결하며 다음 원칙들을 단계적으로 적용함:
  - 토큰을 주소창이 아닌 브라우저 쿠키에 저장
  - DB에는 토큰 원본이 아닌 해시값만 저장 (DB 유출 시에도 토큰 복원 불가)
  - 토큰을 "복구할 때마다 매번" 교체하면 여러 탭·동시 요청이 충돌해 정상 사용자가 로그아웃될 수 있다는 걸 알게 되어, 일정 시간(1시간)이 지난 뒤 다음 사용 시점에만 교체하는 시간 기반 회전 방식으로 수정
  - 이미 교체되어 사용이 끝난 옛 토큰이 다시 나타나면 탈취 시도로 간주해 해당 계정의 모든 세션을 강제 종료하는 재사용 탐지 로직을 추가

### Git/배포 운영

- 로컬에서 MySQL 스키마를 바꾸는 작업(`DROP TABLE` 등)이 배포 환경과 **같은 DB를 공유**하고 있어 즉시 영향을 준다는 걸 인지하게 되어, 스키마 변경은 신중한 시점에 하고 코드 배포·Reboot 역시 신중히게 해야 함을 느낌
